# 新类别提议与新增归档

可靠正文经过已有类别检索，明确判定 `missing-category` 后，使用同一个规划服务的共享模型额度发出 `new-category` 请求。模型提供已有父级（空字符串为顶层）、不带编号的名称、正文理由及查找收益；程序在相同父级复用已有同义名，分配完整层级编号，并按知识库根、完整父级及名称协调相同提议。不同领域的“基础”“实践”等同名叶类别不会被强行归并到另一父级；跨领域复用仍由前置已有类别检索判断。首份材料即可提出必要类别，不使用固定篇数阈值。

公共收件箱分类结果包含 `newCategory`：`proposalId`、`proposalHash`、`path`、`parent`、`label`、`reason`、`benefit`。建议与审核均不创建分类目录。`POST /api/inbox/review` 选择新类别时必须同时提交 `acceptNewCategory:true` 和当前 `newCategoryHash`；选择现有类别无需接受新提议。任意路径、陈旧或篡改摘要不能取得创建授权。

文件冻结计划同时绑定原分类目录版本与完整提议。知识库归档入口只把已审核的选中项传给现有 `confirmNewArchive`。同次授权明确列出的新提议进入每份依赖文件的归档日志；执行器仅允许这些提议产生的目录差异，其他目录或说明变化仍阻断旧审核。未选中的已审核文件不会因为本次建类而自动获得新版本授权。

执行器在来源、关联、外部写入、首次摄取设置和链接检查通过后，先保存类别创建意图，再创建目录及 `.category.json` 说明，最后按原归档日志复制、验证及移除来源。同提议只创建一次；精确的提议摘要及分类说明证明允许后续依赖复用。已有路径或大小写冲突保留来源。类别创建或后续归档失败保存冻结提议、创建事件和错误，依赖文件不算成功，同次授权停止后续写入。

重启只读取结果。对于日志证明来源仍在、文件尚未复制或已经完整复制的失败现场，可沿用公开 `batches/getReport` 提供的 `applySlice` 恢复动作；类别说明不完整或被外部占用时继续阻断并保留现场，需人工核对，不自动删除或覆盖目录。

模型列出的已有类别 `rename`、`merge`、`move` 仅通过 `adjustments` 展示涉及的类别、历史材料影响、理由和收益；普通新增归档不执行这些调整。实际历史改名、合并、迁移仍必须走原有完整目录方案、副本验证、备份、恢复演练及原库确认流程。

## 测试夹具清理修复证据

联合执行分类审核与分析检查点测试时，分类审核第四项曾发生 `ENOTEMPTY: directory not empty, rmdir`（Windows errno `-4051`）。旧夹具先由 `migrationFixture` 注册删除目录钩子，再注册服务关闭钩子；删除失败后，后续关闭未执行，测试子进程保留监听并一直存活。这是本轮新增夹具问题，不能作为既有基线跳过。

`test/http-fixture-cleanup.test.js` 用两个真实 HTTP 服务模拟目录删除失败。沿用旧的先删除后关闭顺序时，删除失败后仍能访问服务器，测试出现 `Missing expected rejection` 红灯。修复后的测试还证明一个目录删除失败时，第二个临时目录继续清理，所有监听均不可访问，重复关闭幂等。

分类审核与新增分类夹具均改用 `migrationFixture(t,{retained:true})`，同一个测试的多个临时库和重启服务统一登记至 `httpFixtureScope`。唯一清理钩子先关闭全部服务器，使用 `closeAllConnections`、五秒关闭界限和幂等关闭；随后逐一清理目录，设置五次重试及一百毫秒间隔。关闭或删除出错仍完成其他资源清理，最后汇总错误。公共 HTTP 请求设置十五秒超时，不通过修改生产代码掩盖夹具失败。

合并分析检查点与公平调度后，分类审核、新类别、清理回归、页面、检查点及调度联合焦点测试为 25 项全通过。最终全量结果由集成交付证据记录，原始输出保存在任务的 `.scratch/implement-41/45-focus-final.txt` 与 `45-full-final.txt`。
